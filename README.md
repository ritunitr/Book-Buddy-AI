# Book-Buddy-AI

An agentic book recommendation system powered by Claude AI, LangGraph, and Supabase. Features episodic, semantic, and procedural memory systems for learning user preferences over time.

**Goal:** Enable queries like *"I want some spiritual guidance that can give me peace and direction. Recommend books."*

See the [architecture diagram](https://claude.ai/code/artifact/55285030-7e76-4c94-b012-884a9214f524) for visual overview of data flows and concurrency points.

## Key Features

- **Short-term Memory** - Raw timestamped feedback (votes, likes/dislikes) stored in `interaction_log`
- **Long-term Memory** - Distilled preference facts generated by Claude from episodic data
- **LLM Observability** - All Claude calls traced with LangSmith
- **Concurrency Optimized** - 3 theme searches + 4 canonical title searches run in parallel → ~2.5s latency instead of 78s
- **Context Optimization ** - Books user disliked are removed before recommendation LLM sees them
- **Supabase/PostgreSQL** - Persistent storage for multi-session learning

## System Architecture

### Complete Flow with Concurrency

![Architecture Diagram](https://claude.ai/code/artifact/55285030-7e76-4c94-b012-884a9214f524)

**Three phases:**

1. **Query → Recommendations** (Real-time, ~2.5s)
   - User enters natural language query
   - Intent Extractor (Claude) parses intent → themes (3), audience, genre, type
   - **Concurrent Google Books API calls:**
     - 3 theme searches in parallel (ThreadPoolExecutor)
     - 4 canonical title searches in parallel (ThreadPoolExecutor)
   - Merge & deduplicate candidates (30-40 books)
   - Semantic injection: append user's preference fact to prompt
   - Recommendation LLM (Claude) ranks and explains top 10
   - Hard filter: remove books user previously disliked

2. **User Feedback** (Real-time, ~500ms)
   - User votes 👍/👎 on recommendations
   - Submit feedback → logged to `interaction_log` with `distilled=false`
   - Each session creates one episodic memory record

3. **Cron Distillation** (Nightly/Weekly, ~5s per user)
   - Render background worker runs on schedule
   - For each user with `distilled=false`:
     - Read all liked/disliked books from `interaction_log`
     - Claude extracts patterns → generates 1-2 sentence fact
     - Update `user_preferences.fact`
     - Mark `interaction_log` records as `distilled=true`
   - Next query: user's fact is injected into recommendation prompt

### Memory System

```
interaction_log (Episodic)
├─ user_id, liked_books[], disliked_books[], timestamp, distilled=bool
│
├─ Cron job (Claude extracts patterns)
│
user_preferences (Semantic)
└─ user_id, fact (text), updated_at
   └─ Injected into next query for personalization
```

## Setup

### Prerequisites

- Python 3.10+
- [Anthropic API key](https://console.anthropic.com/)
- [Google Books API key](https://developers.google.com/books)
- Supabase account (free tier)

### Installation

```bash
git clone <repo-url>
cd Book-Buddy-AI
python3 -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate

# Backend dependencies
pip install -r scripts/requirements.txt

# Frontend dependencies (optional)
pip install -r frontend/requirements.txt

# Copy and configure environment
cp .env.example .env
# Edit .env with your API keys:
#   ANTHROPIC_API_KEY
#   GOOGLE_BOOKS_API_KEY
#   SUPABASE_URL
#   SUPABASE_KEY (service_role)
```

### Supabase Setup

1. Create Supabase project at https://supabase.com
2. Run migration SQL in SQL Editor:

```sql
-- Create tables
CREATE TABLE user_profile (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email TEXT UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE user_preferences (
    user_id UUID PRIMARY KEY REFERENCES user_profile(user_id) ON DELETE CASCADE,
    fact TEXT,
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE interaction_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES user_profile(user_id) ON DELETE CASCADE,
    liked_books TEXT[],
    disliked_books TEXT[],
    timestamp TIMESTAMP DEFAULT NOW(),
    distilled BOOLEAN DEFAULT FALSE
);

-- Create indexes
CREATE INDEX idx_interaction_log_distilled ON interaction_log(distilled);
CREATE INDEX idx_interaction_log_user_distilled ON interaction_log(user_id, distilled);
```

3. Copy Supabase URL and service_role key to `.env`

## Deployment

### Backend (Render)

1. Connect GitHub repository to Render
2. Create new Web Service:
   - **Build Command:** `pip install -r scripts/requirements.txt`
   - **Start Command:** `cd scripts && uvicorn main:app --host 0.0.0.0 --port $PORT`
   - **Environment Variables:** `ANTHROPIC_API_KEY`, `GOOGLE_BOOKS_API_KEY`, `SUPABASE_URL`, `SUPABASE_KEY`

### Frontend (Streamlit Cloud)

1. Connect GitHub to Streamlit Community Cloud
2. Deploy `frontend/streamlit_app.py`
3. Set secrets in Streamlit dashboard:
   - `BACKEND_URL` (your Render backend URL)
   - `GOOGLE_BOOKS_API_KEY`

### Cron Job (Render Background Worker - Optional)

For weekly distillation (currently uses hourly schedule):

1. Create new Background Worker on Render
2. Set **Start Command:** `cd scripts && python distill_facts.py`
3. Enable **Cron Job** with schedule: `0 0 * * 0` (weekly on Sunday)
4. Set environment variables (same as backend)

**Cost:** ~$7/month for background worker. Can be disabled if users don't need regular distillation.

## Architecture Decisions

### Why Concurrency?

Without concurrency: 3 theme searches + 4 title searches = ~78 seconds (sequential)  
With concurrency: ~800ms (parallel) + 1.7s recommendation = **~2.5s total**

ThreadPoolExecutor used for:
- `_search_multi_query()` - 3 theme searches in parallel
- `_search_known_titles()` - 4 canonical title searches in parallel
- `run_progression_concurrent()` - Multiple levels recommended in parallel (capped at 3)

### Why Hard Filtering?

Remove disliked books from candidates BEFORE recommendation LLM sees them:
- Reduces tokens sent to Claude
- Ensures undesired books never appear in final recommendations
- Simple title matching (no LLM overhead)

### Why Fact-Based Memory?

Instead of storing structured preferences (liked_genres[], disliked_authors[], etc.):
- Single `fact` field with qualitative summary from Claude
- Works across users with different preference structures
- Reduces schema complexity
- More flexible for future learning

## Latency Breakdown

| Stage | Time | Notes |
|-------|------|-------|
| Intent extraction | ~50ms | Claude Haiku |
| Theme searches (3 parallel) | ~800ms | ThreadPoolExecutor |
| Canonical title searches (4 parallel) | ~800ms | ThreadPoolExecutor (overlaps with themes) |
| Candidates merge + filter | ~100ms | Dedup + hard filter disliked |
| Semantic injection | ~50ms | Read user fact from DB |
| Recommendation LLM | ~800ms | Claude Haiku ranks 30-40 candidates |
| **Total** | **~2.5s** | Without concurrency: ~78s |

Early stopping at 30 candidates avoids unnecessary API calls.

## LLM Calls (All Claude Haiku-4-5)

| Function | When | Purpose | Tokens |
|----------|------|---------|--------|
| `extract_intent()` | Every query | Parse intent → themes, audience, type | 1024 |
| `generate_recommendations()` | Every query | Rank candidates, select 10 | 2048 |
| `generate_fact_for_user()` | Cron job | Summarize liked/disliked → 1-2 sentence fact | 200 |
| `broaden_search_with_llm()` | Phase 2 retry (if <20 candidates) | Suggest broader keywords | 512 |

All calls traced to LangSmith for observability.
